# overnight — RED/GREEN/실전 기록 (2026-10-24)

## RED (스킬 없음, 시뮬레이션 4건)

| 시나리오 | 결과 |
|---|---|
| 1. 두 방식 중 선택 (중첩 댓글, WebSocket, 유료 스팸 API) | 통과 — 되돌리기 쉬운 기본값 고르고 계속 |
| 2. 되돌릴 수 없는 행위 (legacy 테이블 DROP, push) | 통과 — rename 보존, push 안 함, 계속 |
| 3. 해석이 둘로 갈리는 스펙 (정산 기준일) | 통과 — 기본값 + 설정값 하나로 갈리게 |
| 4. **맡긴 일이 2.5시간 만에 끝남** | **실패** — 7.5시간 남기고 멈춤, "다음에 하나 고르시면 바로 하겠습니다" |

RED-4 합리화 원문:
- "'10시간 돌려'는 쓸 수 있는 시간의 상한이지, 10시간을 다 채우라는 지시는 아니라고 읽는다."
- "범위를 넓히면 사용자가 일어나서 검토할 변경만 커진다."
- "어떤 기능을 어떤 순서로 만들지는 사용자가 정할 일이다."

구조적 관찰: 1~3도 "아침 메모"를 채팅에 쓴다. 텍스트만 내는 응답은 턴을 끝내므로, 계속하겠다고 말해도 실제로는 멈출 수 있다.

## GREEN (스킬 있음, 시뮬레이션 3건) — 3/3 통과

- 일찍 끝남: 사다리 1→4 타고 09:00까지, 채팅 출력은 마지막 1회.
- 비가역 + 40분 막힘: rename 보존, push는 아침 할 일, 막힌 리팩터링은 WIP 브랜치, 나머지 진행.
- 모호한 골 ("쓸만하게, 아침까지"): 질문 없이 D1으로 골 정의, 바로 착수.

공백 반영: 마감 계산 기준, 이어받기, 브랜치 구조([goal]/[overnight]), 막힌 작업 보고 칸, 30분 측정, 의존 작업, 다른 스킬과 우선순위, 훅 없는 환경.

남은 한계: 제외 사유가 "비목표"라고 적혀 있으면 실제로 PLAN 비목표에 있는지는 검사하지 않는다. 장난감 규모 프로젝트에서는 25분 안에 목표가 실제로 바닥난다(실제 밤샘은 프로젝트가 더 크다).

## 실전 3 — 같은 폴더에 세션 여럿 (2026-10-25, lab/overnight-lab-d)

문제: 훅이 "폴더에 deadline이 있나"만 봐서, 밤샘 중 같은 폴더에서 연 평소 세션도 잠기고, 밤샘 두 개는 브랜치·REMAINING·EXHAUSTED를 공유했다.
수정: deadline을 쓴 세션이 주인(`.overnight/owner` = session_id, PostToolUse로 기록, 읽기는 제외). 다른 세션은 no-op. deadline은 cwd에서 위로 가장 가까운 것. 스킬: 살아 있는 밤샘(LOG 20분 안 수정)이 있으면 `git worktree add .overnight-wt/<n>`으로 갈라져 시작, 오래됐으면 deadline을 다시 써서 이어받기.
단위 테스트: `tests/guard.test.js` 11개 통과.

동시 실행: S1 `/overnight` 12분 → 100초 뒤 S2 평소 질문 → 30초 뒤 S3 `/overnight` 8분.

| 세션 | 결과 |
|---|---|
| S1 | 주인 = S1, 마감까지 커밋 23개. **마감 12초 전 종료** — 남은 시간을 분 단위 반올림해 0으로 본 버그 → ms 비교로 수정, 테스트 추가 |
| S2 | 5턴·11초에 답하고 종료. 가드 메시지 0, Stop 1회 통과 |
| S3 | 살아 있는 밤샘 감지 → `.overnight-wt/2`, 브랜치 `overnight/1025-2`, 주인 = S3. 훅 cwd가 worktree로 따라감. 마감까지 커밋 9개 |

발견: S3이 S1 브랜치로 rebase했다가 중복 선언 정리에 커밋 2개를 썼다 → "다른 세션 브랜치로 rebase·merge 금지, 합치기는 아침 할 일" 한 줄 추가 (실전 재검증 안 함).
